# Changelog

All notable changes to this project are documented in this file.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versioning follows [Semantic Versioning](https://semver.org/) (`MAJOR.MINOR.PATCH`).

## How this file is maintained

- Day-to-day commits/pushes to a feature branch (e.g. `branch_1x`) do **not** need a changelog entry or a version bump — just add your change under `[Unreleased]` below.
- A version is only cut when a Pull Request is merged into `main`:
  1. Rename `[Unreleased]` to the new version + today's date, e.g. `## [1.1.0] - 2026-08-26`.
  2. Add a fresh empty `[Unreleased]` section above it.
  3. Tag the merge commit on `main`: `git tag v1.1.0 && git push origin v1.1.0`.
  4. Optionally turn the tag into a GitHub Release (`gh release create v1.1.0 --notes-from-tag` or via the GitHub UI) so it shows up under the repo's "Releases" tab.
- Version bump guide: **PATCH** (1.0.x) for fixes/tweaks, **MINOR** (1.x.0) for new features that don't break anything existing, **MAJOR** (x.0.0) for breaking changes (e.g. a change that requires re-running the WordPress installer or breaks an existing mu-plugin's data).

## [1.0.1] - 2026-08-29

### Fixed
- The `branch_1x` → `main` merge (v1.0.0's PR) resurrected an old, pre-`custom-` naming-convention copy of the multilingual plugin (`multilingual-post.php` + `multilingual-post/`) alongside the current `custom-multilingual-post.php` — both define identically-named functions (`mlp_get_or_create_group`, `mlp_get_group_posts`, …), and MU-plugins load every top-level `.php` file in `mu-plugins/` unconditionally, so having both would have been an immediate `Cannot redeclare function` fatal error on every page load. Removed the resurrected old copy. Also removed six root-level `docs/*.md` files from that same much-older history (`db_mysql_manage.md`, `db_mysql_install.md`, `wp_docker_deploy.md`, `wp_manual_install.md`, `cms_php_install.md`, `wp_custom_plugins.md`), superseded entirely by the current `docs/deploy/`, `docs/plugins/`, and `docs/themes/` structure and referenced from nowhere current.

## [1.0.0] - 2026-08-29

### Added
- `comments.php` — the theme had comments open at the data level (`comment_status: open`) but no template calling `comments_template()` anywhere, so the comment list and reply form never actually rendered on a post regardless of that setting. Added a close-to-stock template (`wp_list_comments()` for the list, `comment_form()` for the form — both core, nothing reimplemented, no "Website" field) and wired `single.php` to call it only when `comments_open() || get_comments_number()`, matching WordPress's own convention. Styled as rounded cards rather than a line-separated list, closer to a social feed's comment thread, with two length caps so one busy post can't take over the page: `assets/js/comment-interactions.js` collapses any individual comment past ~4 lines behind a "See more"/"See less" toggle (measured against its actual rendered height, so a short comment is never touched), and `.comment-list` itself caps at `max-height: 32rem` with `overflow-y: auto`, scrolling the whole thread internally once there's enough comments to exceed that instead of pushing the reply form further down the page. No spam/moderation handling added here — that's Settings → Discussion's job (e.g. "Comment must be manually approved"), not a template concern.
- `custom-newsletter-signup` MU-plugin: a Subscribe button that opens a popup to collect an email — heading, email field + button, and a consent checkbox that gates the Submit button (starts disabled in the raw HTML itself, so it fails safe even if the frontend script doesn't load). `core/render.php`'s `mlns_render_signup()` builds the button+popup; `header.php` calls it directly, showing it on every page in the header's action row right after Search (the same slot the old RSS **Subscribe** link used to occupy — see Removed, below) — always there just because this MU-plugin is active, nothing to configure or place. Collection only, deliberately — no `wp_mail()`/Mailchimp-style sending yet, since actually delivering mail reliably is a separate, later decision. Stores addresses in a new `wp_mlns_subscribers` table (created via a version-checked `dbDelta()` on `init`, since MU-plugins never get an activation hook to hang the usual "create table on activation" off of), through a public `POST /mlns/v1/subscribe` REST route guarded by a honeypot field (returns a fake success without inserting, so a bot doesn't learn it's being checked), a server-side-enforced consent flag, and `is_email()` validation — a duplicate email is treated as a success (`already_subscribed`) rather than an error. The modal is moved to be a direct child of `<body>` on init, so a `position: fixed` popup always centers against the actual viewport rather than whatever ancestor it happens to be nested under (an ancestor with `transform`/`filter`/`backdrop-filter` set becomes the containing block instead). **Settings → Newsletter Subscribers** lists collected addresses with a CSV export, since collecting them into a table nobody can read back out wouldn't be a usable feature. Documented in [`docs/plugins/custom-newsletter-signup.md`](../docs/plugins/custom-newsletter-signup.md).
- `custom-post-tabs` MU-plugin: a "Post Tabs" block with two tabs — Latest (newest first) and Discussions (most-commented first, via `orderby: comment_count`, data WordPress core already tracks) — switchable without a page reload (both tabs render server-side up front, `assets/tabs.js` just toggles which is visible). No "Top" (by view count) tab yet, since WordPress has no native popularity/view metric to sort by — that needs its own view-counter plugin and decision later, not bundled in here. Each row shows the post's Featured Image cropped to a dedicated `mlpt-thumb` size (320×200), same reasoning as `custom-featured-carousel`'s `mlfc-carousel` size. Each tab is paginated at the configured posts-per-tab count, with "1 2 3 … 100"-style numbered pagination (`mlpt_page_number_sequence()`, not `paginate_links()` — these are buttons that fetch a page over a new public `/mlpt/v1/posts` REST route, not `<a href>` navigation) — the initial page renders server-side, every page after that swaps in over REST so a long archive is never fully preloaded just to view "Latest". Documented in [`docs/plugins/custom-post-tabs.md`](../docs/plugins/custom-post-tabs.md).
- `docs/deploy/` (files named `<topic>-<step>.md` for anything host-agnostic, `<platform>-<step>.md` — e.g. `wp-*`, `inet-*`, `github-*` — for anything specific to one platform) — hosting (shared "SSD" cPanel hosting, not a VPS — matches the reasoning already in `README.md`), domain registration and DNS configuration as separate steps, the one-time initial WordPress setup (DB, WordPress core, `wp-config.php` with `DISALLOW_FILE_EDIT`/`DISALLOW_FILE_MODS` set so real changes can only happen through git), and the ongoing GitHub → production sync (rsync-over-SSH or FTP, optionally automated via a GitHub Actions workflow). Every path is scoped to exactly `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/`, the same two directories this repo has ever tracked — a deploy is never a wholesale copy of the repo onto the server, matching `CLAUDE.md`'s "core stays untouched" rule. `hosting-requirements.md` also walks through this project's actual checkout (iNET) as a worked example, down to the specific tier bought — WP-H1, the cheapest of three tiers that differ only in site/CPU/RAM allowance (security and platform features are identical across all three) — and confirms its bundled free SSL (ZeroSSL) and daily backups make a separately-sold SSL product, a premium email add-on, and "Cloud Server" (a VPS under another name) all unnecessary for this project's scale. `inet-onepanel-setup.md` maps that same checklist onto **1Panel** ("OnePanel"), the control panel this project's iNET plan actually runs on rather than cPanel — where each step lives, and a real gotcha: 1Panel's own Git Manager clones straight into a site's document root, which would dump this repo's own root files onto the live site instead of a working WordPress install, since only `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/` are meant to reach production. A plain `git clone` over SSH into a separate directory (confirmed available on this plan) is the correct equivalent. `inet-dns-setup.md` maps `dns-configuration.md`'s Option B onto iNET's actual portal (`portal.inet.vn` → Tên miền → Bản ghi), per [iNET's own guide](https://helpdesk.inet.vn/knowledgebase/huong-dan-tro-ten-mien-ve-hosting) — confirms iNET has no nameserver-delegation option, only manual A/CNAME records, and that records apply within ~30 minutes.
- `.github/workflows/deploy.yml` — the real (not just documented) CI/CD workflow: rsync-over-SSH of `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/` to production, triggered only by a push to `main` (never `branch_1x` — see `docs/deploy/github-workflows.md`'s "Which branch actually deploys"). Deploy host/user/key and even the two target paths are GitHub Actions secrets rather than hardcoded, so the workflow file itself never encodes this hosting account's real layout.
- Docker-based local dev environment: `docker/docker-compose.yml` running WordPress (Apache + PHP 8.2) and MySQL 8.0 as separate, networked services, both set to `restart: unless-stopped` so they come back up on their own after the machine reboots (colima itself auto-starts via `brew services`) — `localhost:8000` should just work whenever you need it during dev, no manual restart step.
- `docker/wp-config.docker.php` — wp-config template that reads DB credentials from environment variables instead of being hand-edited.
- `custom-multilingual-post` MU-plugin: manual (not auto) translations grouped by post meta, all served from **one shared URL** — a `?lang=` toggle swaps content in place on the original post's permalink, translation posts' own permalinks 301-redirect back to it, and `hreflang` tags are emitted for the languages actually published. Editing happens through a native-feeling **Multilingual** panel in the post-edit sidebar (a real `PluginDocumentSettingPanel`, `SelectControl`/`Button`/`Notice` from `@wordpress/components` — not a classic metabox): a language dropdown wired to a proper `register_post_meta()` field, a live translation list, and an "Add translation" flow backed by two `/mlp/v1/` REST routes (replacing the earlier admin-ajax + nonce approach). Plus a `[language_switcher]` shortcode for the frontend toggle.
- `docs/plugins/` — one doc file per custom plugin explaining how it works, starting with [`custom-multilingual-post.md`](../docs/plugins/custom-multilingual-post.md). New custom plugins should add their own doc here going forward.
- `minimal-reader` custom theme (`public/wp-content/themes/minimal-reader`) — a from-scratch classic theme matching the earlier Payload/Next.js frontend's design system: warm white/near-black surfaces with one burnt-orange accent (light + dark via a flicker-free `data-theme` toggle), Source Serif 4 for headings/body copy, one centered ~48rem reading column, and styling for the `custom-multilingual-post` language switcher. `.gitignore` now tracks this theme folder specifically (it previously excluded all of `wp-content/themes/`, which would have silently dropped any custom theme from version control). Documented in [`docs/themes/custom-minimal-reader.md`](../docs/themes/custom-minimal-reader.md).
- Substack-style homepage: `page-templates/template-home.php` (an ordinary WP Page template, selectable from Page Attributes). The site is now set up with a "Home" Page (this template) as the static front page and a separate "Blog" Page as `page_for_posts`.
- `custom-featured-carousel` MU-plugin — a "Featured Carousel" block: a full-width, auto-advancing carousel, insertable/removable/movable anywhere (it's a feature, not a layout, so it lives in a plugin, not the theme). No fallback data source — add posts by pasting their link (resolved to a post over the REST API, works with plain `?p=` or pretty-permalink URLs), up to 10, drag-and-drop to reorder (native HTML5 DnD, no library), and renders nothing until at least one is added. Slide delay (ms) is also configurable per-block. Manual navigation via prev/next arrows, dots, two-finger trackpad swipe (`wheel` event, deltaX-dominant), and touch swipe — any of which restarts the autoplay clock. `assets/carousel.js` (vanilla JS, pauses on hover/focus, respects `prefers-reduced-motion`) only loads on pages that actually use the block, via `has_block()`. Falls back to a plain accent-colored card when a featured post has no thumbnail. Documented in [`docs/plugins/custom-featured-carousel.md`](../docs/plugins/custom-featured-carousel.md).
- `custom-table-of-contents` MU-plugin: a "Table of Contents" block for the editor inserter, replacing the auto-ToC block that existed in the old Payload CMS but wasn't carried over during migration. No build tooling — the editor UI is plain JS (`wp.blocks`/`wp.element`), and the frontend markup is a dynamic PHP `render.php` (via `block.json`'s `"render"` field). Rebuilds its link list from the post's actual headings on every view, so there's no separate "sync" step. Documented in [`docs/plugins/custom-table-of-contents.md`](../docs/plugins/custom-table-of-contents.md).
- `custom-maintenance-mode` MU-plugin: a site-wide maintenance toggle matching the old Payload CMS's `maintenance` global — one on/off switch plus a custom title/message (**Settings → Maintenance Mode**), replacing the whole page with a `503` for every visitor except a logged-in administrator. Self-styled (doesn't depend on the active theme's stylesheet) since it needs to render no matter what theme is active. Documented in [`docs/plugins/custom-maintenance-mode.md`](../docs/plugins/custom-maintenance-mode.md).
- Naming convention for this project's own hand-written plugins: `custom-<what-it-does>` (e.g. `custom-multilingual-post`, `custom-table-of-contents`, `custom-maintenance-mode`), so they're easy to tell apart from anything installed from WordPress.org at a glance. The two plugins that predated this convention were renamed to match (folders, loader files, and their `docs/plugins/` entries).
- Page-to-page transitions via the native **Cross-Document View Transitions API** (`@view-transition { navigation: auto; }` in `style.css`) — no JavaScript, no SPA router: a supporting browser cross-fades between full navigations automatically, an unsupported one just ignores the unknown at-rule and navigates normally, and `prefers-reduced-motion: reduce` gets the same plain navigation either way. `.site-header` carries a `view-transition-name` so it morphs in place across the navigation instead of cross-fading, closer to Substack's "just the tab changed" feel without actually being a single-page app.
- Redesigned `header.php` to match a Substack-style masthead: site title centered above a nav row (active item underlined via WordPress's own `current-menu-item` class — no menu is assigned to "Primary Menu" yet, so that row won't show until one is under Appearance → Menus), with search/share icon buttons, a Subscribe link (points at the site's native RSS feed — `get_feed_link()`, nothing new to build), and a Sign in link for logged-out visitors (`wp_login_url()`) on the right. Search toggles a hidden native `get_search_form()` panel; Share opens a Substack-style dropdown (Copy link, Send as email, Facebook, LinkedIn, Bluesky, X — each a plain share-intent URL or `mailto:`, resolved client-side, no API keys). New `assets/js/header-interactions.js` for both. Documented in [`docs/themes/custom-minimal-reader.md`](../docs/themes/custom-minimal-reader.md).

### Changed
- Masthead layout: site title moved from absolutely-centered to sitting naturally on the left, `.site-header__actions` pushed to the right via `justify-content: space-between`, and the header row's 1024px reading-column cap removed (`max-width: none`) so both ends actually reach the browser's edges on wide screens. Search changed from a full-width panel dropping below the whole header into a pill that expands inline from the search icon itself (CSS width transition, `position: absolute` so it doesn't reflow the other action buttons) — the pill's border/background live on one wrapper around a borderless input rather than two separately-bordered controls, avoiding a visible seam where they used to meet. WordPress's default search-form submit button stays in the DOM (Enter still submits, still reachable via screen readers) but is visually hidden the accessible way, since a visible "Search" button doesn't fit a compact pill.
- The homepage template (`page-templates/template-home.php`) is now a blank canvas — no hardcoded hero, category nav, or feed, just the Page's own content, full width. The homepage is built entirely out of blocks instead, editable and rearrangeable in the UI: core Paragraph/Heading for an intro, the core Categories block for a category nav, a core Query Loop for the posts feed (fully configurable — count, order, filters, per-post fields, all in the block's own UI), and the new Featured Carousel block for a pinned-posts spotlight. `minimal-reader` now ships default styling for those core blocks (`.wp-block-post-title`, `.wp-block-categories-list`, `.wp-block-post-template`, …) so a page built purely from them already matches the site's look.

### Removed
- The header's **Sign in** link (`wp_login_url()`) — this project's admin logs in by going straight to `/wp-admin`, not a public header link, so it only ever served the site's own author. A separate, future concern is registered-reader login for commenting on the eventual Payload-based version of this site — a distinct feature from this theme's admin sign-in link, not a reason this one needs to exist.
- The header's RSS **Subscribe** link (`get_feed_link()`) — labeling a link to raw RSS XML "Subscribe" read as an email-collection CTA it never was. `custom-newsletter-signup`'s button now occupies that same header slot instead (see Added, above). RSS itself is untouched: the feed still exists and is still auto-discovered via the `<link rel="alternate">` tag `wp_head()` already emits, it just no longer has a header button of its own pointing at it.

### Fixed
- `custom-featured-carousel`'s autoplay could get stuck paused indefinitely: hovering/focusing the carousel then switching to a different browser tab never fires `mouseleave`/`focusout` on the now-hidden page, so returning to the tab left it in a permanent "still hovering" state until an unrelated mouse move happened to pass over it. Hover/focus are now tracked as flags (also fixing a related bug where hovering and focusing at once, then only one ending, incorrectly resumed autoplay) and reset on `visibilitychange` back to visible rather than trusted.
- `custom-featured-carousel` was fetching WordPress core's `large` image size (max 1024px, uncropped) and applying it as a CSS `background-image` — capped resolution upscaled blurry in the carousel's full-bleed hero, and a `background-image` never gets WordPress's automatic `srcset`/`sizes`, so the browser always fetched that one fixed-resolution file regardless of viewport size or pixel density. Registered a dedicated `mlfc-carousel` image size (1600×500, hard-cropped) and switched to a real `<img>` via `get_the_post_thumbnail()`, so the browser picks the right resolution itself.
- `mlr-style`, `mlr-theme-toggle`, and `mlr-header-interactions` were enqueued with the theme's static `Version` string as the cache-busting query param — a hardcoded number that never changes between edits, so browsers kept serving stale cached CSS/JS after every change instead of picking up the new file. Switched all three to `filemtime()`, matching how every MU-plugin in this project already versions its own assets.
- Dockerfile was missing the `mysqli`/`pdo_mysql`/`gd`/`zip` PHP extensions required by WordPress — added their install step.
- `custom-multilingual-post`: translation posts (not the group's original) could show up as their own separate entry in list views (home, blog, archives) since they're real published WP posts — added a `pre_get_posts` filter, plus a reusable `mlp_exclude_translations_meta_query()` helper for custom queries like the new home feed, so only the group's one canonical post is ever listed.
- `the_excerpt()` already wraps its output in a `<p>` (WordPress hooks `wpautop` onto the `the_excerpt` filter) — the theme's post list and home feed were wrapping it in another `<p>`, producing invalid nested `<p><p>…</p></p>` markup. Switched both containers to `<div>`.
- `wp-content/uploads` (the `wp_uploads` Docker volume) ended up root-owned instead of `www-data`-owned, since the directory doesn't exist in the WordPress core zip and Docker created it fresh on first mount — every media upload failed with "Unable to create directory". Dockerfile now pre-creates `wp-content/uploads` before the final `chown`, so a fresh volume picks up the right ownership from the image.
- `add_editor_style()` was pointed at the full `style.css`, whose flicker-prevention rule (`html { opacity: 0 }`, undone only by an inline script that runs on the frontend, never inside the editor's iframe) left the whole block-editor canvas permanently invisible. Split off a dedicated `assets/css/editor.css` (tokens + content typography + the Table of Contents block's look) with no such rule.
- `custom-table-of-contents`'s block wasn't appearing in the inserter at all: block.json's bare `"editorScript": "file:./editor.js"` only picks up dependencies from an `editor.asset.php` file, which only exists when a build tool generates one — without it, WordPress registered the script with an *empty* dependency array, and `wp.blocks.registerBlockType()` silently refuses to register a block whose settings are missing `title`/`category`/etc. (no console crash, it just never shows up). Fixed by explicitly `wp_register_script()`-ing the script with the right `wp-blocks`/`wp-element`/`wp-block-editor`/`wp-i18n` dependencies and passing that handle to `register_block_type()` via `'editorScript' => ...` (must be that exact camelCase key — a `editor_script` override is silently ignored), and by declaring the same title/category/icon/attributes directly in the JS `registerBlockType()` call.
- `single.php` no longer hardcodes an author/date/category line above the post — inserted metadata like that should come from you explicitly adding WordPress's own Post Date/Post Author/Post Terms blocks to a post, not from the theme silently rendering it for every post whether you asked for it or not.
