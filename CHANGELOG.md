# Changelog

All notable changes to this project are documented in this file.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versioning follows [Semantic Versioning](https://semver.org/) (`MAJOR.MINOR.PATCH`).

## How this file is maintained

- Day-to-day commits/pushes to a feature branch (e.g. `branch_1x`) do **not** need a changelog entry or a version bump — just add your change under `[Unreleased]` below.
- A version is only cut when a Pull Request is merged into `main`:
  1. Rename `[Unreleased]` to the new version + today's date, e.g. `## [1.1.0] - 2026-08-26`.
  2. Add a fresh empty `[Unreleased]` section above it.
  3. Tag the merge commit on `main`: `git tag v1.1.0 && git push origin v1.1.0`.
  4. Optionally turn the tag into a GitHub Release (`gh release create v1.1.0 --notes-from-tag` or via the GitHub UI) so it shows up under the repo's "Releases" tab.
- Version bump guide: **PATCH** (1.0.x) for fixes/tweaks, **MINOR** (1.x.0) for new features that don't break anything existing, **MAJOR** (x.0.0) for breaking changes (e.g. a change that requires re-running the WordPress installer or breaks an existing mu-plugin's data).

## [Unreleased]

### Added
- `docs/deploy/` (files named `<topic>-<step>.md` for anything host-agnostic, `<platform>-<step>.md` — e.g. `wp-*`, `onepanel-*`, `github-*` — for anything specific to one platform) — hosting (shared "SSD" cPanel hosting, not a VPS — matches the reasoning already in `README.md`), domain registration and DNS configuration as separate steps, the one-time initial WordPress setup (DB, WordPress core, `wp-config.php` with `DISALLOW_FILE_EDIT`/`DISALLOW_FILE_MODS` set so real changes can only happen through git), and the ongoing GitHub → production sync (rsync-over-SSH or FTP, optionally automated via a GitHub Actions workflow). Every path is scoped to exactly `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/`, the same two directories this repo has ever tracked — a deploy is never a wholesale copy of the repo onto the server, matching `CLAUDE.md`'s "core stays untouched" rule. `hosting-requirements.md` also walks through this project's actual checkout (iNET) as a worked example, down to the specific tier bought — WP-H1, the cheapest of three tiers that differ only in site/CPU/RAM allowance (security and platform features are identical across all three) — and confirms its bundled free SSL (ZeroSSL) and daily backups make a separately-sold SSL product, a premium email add-on, and "Cloud Server" (a VPS under another name) all unnecessary for this project's scale. `onepanel-setup.md` maps that same checklist onto **1Panel** ("OnePanel"), the control panel this project's iNET plan actually runs on rather than cPanel — where each step lives, and a real gotcha: 1Panel's own Git Manager clones straight into a site's document root, which would dump this repo's own root files onto the live site instead of a working WordPress install, since only `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/` are meant to reach production. A plain `git clone` over SSH into a separate directory (confirmed available on this plan) is the correct equivalent.
- `.github/workflows/deploy.yml` — the real (not just documented) CI/CD workflow: rsync-over-SSH of `wp-content/mu-plugins/` and `wp-content/themes/minimal-reader/` to production, triggered only by a push to `main` (never `branch_1x` — see `docs/deploy/github-workflows.md`'s "Which branch actually deploys"). Deploy host/user/key and even the two target paths are GitHub Actions secrets rather than hardcoded, so the workflow file itself never encodes this hosting account's real layout.
- Docker-based local dev environment: `docker/docker-compose.yml` running WordPress (Apache + PHP 8.2) and MySQL 8.0 as separate, networked services, both set to `restart: unless-stopped` so they come back up on their own after the machine reboots (colima itself auto-starts via `brew services`) — `localhost:8000` should just work whenever you need it during dev, no manual restart step.
- `docker/wp-config.docker.php` — wp-config template that reads DB credentials from environment variables instead of being hand-edited.
- `custom-multilingual-post` MU-plugin: manual (not auto) translations grouped by post meta, all served from **one shared URL** — a `?lang=` toggle swaps content in place on the original post's permalink, translation posts' own permalinks 301-redirect back to it, and `hreflang` tags are emitted for the languages actually published. Editing happens through a native-feeling **Multilingual** panel in the post-edit sidebar (a real `PluginDocumentSettingPanel`, `SelectControl`/`Button`/`Notice` from `@wordpress/components` — not a classic metabox): a language dropdown wired to a proper `register_post_meta()` field, a live translation list, and an "Add translation" flow backed by two `/mlp/v1/` REST routes (replacing the earlier admin-ajax + nonce approach). Plus a `[language_switcher]` shortcode for the frontend toggle.
- `docs/plugins/` — one doc file per custom plugin explaining how it works, starting with [`custom-multilingual-post.md`](../docs/plugins/custom-multilingual-post.md). New custom plugins should add their own doc here going forward.
- `minimal-reader` custom theme (`public/wp-content/themes/minimal-reader`) — a from-scratch classic theme matching the earlier Payload/Next.js frontend's design system: warm white/near-black surfaces with one burnt-orange accent (light + dark via a flicker-free `data-theme` toggle), Source Serif 4 for headings/body copy, one centered ~48rem reading column, and styling for the `custom-multilingual-post` language switcher. `.gitignore` now tracks this theme folder specifically (it previously excluded all of `wp-content/themes/`, which would have silently dropped any custom theme from version control). Documented in [`docs/themes/minimal-reader.md`](../docs/themes/minimal-reader.md).
- Substack-style homepage: `page-templates/template-home.php` (an ordinary WP Page template, selectable from Page Attributes). The site is now set up with a "Home" Page (this template) as the static front page and a separate "Blog" Page as `page_for_posts`.
- `custom-featured-carousel` MU-plugin — a "Featured Carousel" block: a full-width, auto-advancing carousel, insertable/removable/movable anywhere (it's a feature, not a layout, so it lives in a plugin, not the theme). No fallback data source — add posts by pasting their link (resolved to a post over the REST API, works with plain `?p=` or pretty-permalink URLs), up to 10, drag-and-drop to reorder (native HTML5 DnD, no library), and renders nothing until at least one is added. Slide delay (ms) is also configurable per-block. Manual navigation via prev/next arrows, dots, two-finger trackpad swipe (`wheel` event, deltaX-dominant), and touch swipe — any of which restarts the autoplay clock. `assets/carousel.js` (vanilla JS, pauses on hover/focus, respects `prefers-reduced-motion`) only loads on pages that actually use the block, via `has_block()`. Falls back to a plain accent-colored card when a featured post has no thumbnail. Documented in [`docs/plugins/custom-featured-carousel.md`](../docs/plugins/custom-featured-carousel.md).
- `custom-table-of-contents` MU-plugin: a "Table of Contents" block for the editor inserter, replacing the auto-ToC block that existed in the old Payload CMS but wasn't carried over during migration. No build tooling — the editor UI is plain JS (`wp.blocks`/`wp.element`), and the frontend markup is a dynamic PHP `render.php` (via `block.json`'s `"render"` field). Rebuilds its link list from the post's actual headings on every view, so there's no separate "sync" step. Documented in [`docs/plugins/custom-table-of-contents.md`](../docs/plugins/custom-table-of-contents.md).
- `custom-maintenance-mode` MU-plugin: a site-wide maintenance toggle matching the old Payload CMS's `maintenance` global — one on/off switch plus a custom title/message (**Settings → Maintenance Mode**), replacing the whole page with a `503` for every visitor except a logged-in administrator. Self-styled (doesn't depend on the active theme's stylesheet) since it needs to render no matter what theme is active. Documented in [`docs/plugins/custom-maintenance-mode.md`](../docs/plugins/custom-maintenance-mode.md).
- Naming convention for this project's own hand-written plugins: `custom-<what-it-does>` (e.g. `custom-multilingual-post`, `custom-table-of-contents`, `custom-maintenance-mode`), so they're easy to tell apart from anything installed from WordPress.org at a glance. The two plugins that predated this convention were renamed to match (folders, loader files, and their `docs/plugins/` entries).
- Page-to-page transitions via the native **Cross-Document View Transitions API** (`@view-transition { navigation: auto; }` in `style.css`) — no JavaScript, no SPA router: a supporting browser cross-fades between full navigations automatically, an unsupported one just ignores the unknown at-rule and navigates normally, and `prefers-reduced-motion: reduce` gets the same plain navigation either way. `.site-header` carries a `view-transition-name` so it morphs in place across the navigation instead of cross-fading, closer to Substack's "just the tab changed" feel without actually being a single-page app.
- Redesigned `header.php` to match a Substack-style masthead: site title centered above a nav row (active item underlined via WordPress's own `current-menu-item` class — no menu is assigned to "Primary Menu" yet, so that row won't show until one is under Appearance → Menus), with search/share icon buttons, a Subscribe link (points at the site's native RSS feed — `get_feed_link()`, nothing new to build), and a Sign in link for logged-out visitors (`wp_login_url()`) on the right. Search toggles a hidden native `get_search_form()` panel; Share opens a Substack-style dropdown (Copy link, Send as email, Facebook, LinkedIn, Bluesky, X — each a plain share-intent URL or `mailto:`, resolved client-side, no API keys). New `assets/js/header-interactions.js` for both. Documented in [`docs/themes/minimal-reader.md`](../docs/themes/minimal-reader.md).

### Changed
- The homepage template (`page-templates/template-home.php`) is now a blank canvas — no hardcoded hero, category nav, or feed, just the Page's own content, full width. The homepage is built entirely out of blocks instead, editable and rearrangeable in the UI: core Paragraph/Heading for an intro, the core Categories block for a category nav, a core Query Loop for the posts feed (fully configurable — count, order, filters, per-post fields, all in the block's own UI), and the new Featured Carousel block for a pinned-posts spotlight. `minimal-reader` now ships default styling for those core blocks (`.wp-block-post-title`, `.wp-block-categories-list`, `.wp-block-post-template`, …) so a page built purely from them already matches the site's look.

### Fixed
- Dockerfile was missing the `mysqli`/`pdo_mysql`/`gd`/`zip` PHP extensions required by WordPress — added their install step.
- `custom-multilingual-post`: translation posts (not the group's original) could show up as their own separate entry in list views (home, blog, archives) since they're real published WP posts — added a `pre_get_posts` filter, plus a reusable `mlp_exclude_translations_meta_query()` helper for custom queries like the new home feed, so only the group's one canonical post is ever listed.
- `the_excerpt()` already wraps its output in a `<p>` (WordPress hooks `wpautop` onto the `the_excerpt` filter) — the theme's post list and home feed were wrapping it in another `<p>`, producing invalid nested `<p><p>…</p></p>` markup. Switched both containers to `<div>`.
- `wp-content/uploads` (the `wp_uploads` Docker volume) ended up root-owned instead of `www-data`-owned, since the directory doesn't exist in the WordPress core zip and Docker created it fresh on first mount — every media upload failed with "Unable to create directory". Dockerfile now pre-creates `wp-content/uploads` before the final `chown`, so a fresh volume picks up the right ownership from the image.
- `add_editor_style()` was pointed at the full `style.css`, whose flicker-prevention rule (`html { opacity: 0 }`, undone only by an inline script that runs on the frontend, never inside the editor's iframe) left the whole block-editor canvas permanently invisible. Split off a dedicated `assets/css/editor.css` (tokens + content typography + the Table of Contents block's look) with no such rule.
- `custom-table-of-contents`'s block wasn't appearing in the inserter at all: block.json's bare `"editorScript": "file:./editor.js"` only picks up dependencies from an `editor.asset.php` file, which only exists when a build tool generates one — without it, WordPress registered the script with an *empty* dependency array, and `wp.blocks.registerBlockType()` silently refuses to register a block whose settings are missing `title`/`category`/etc. (no console crash, it just never shows up). Fixed by explicitly `wp_register_script()`-ing the script with the right `wp-blocks`/`wp-element`/`wp-block-editor`/`wp-i18n` dependencies and passing that handle to `register_block_type()` via `'editorScript' => ...` (must be that exact camelCase key — a `editor_script` override is silently ignored), and by declaring the same title/category/icon/attributes directly in the JS `registerBlockType()` call.
- `single.php` no longer hardcodes an author/date/category line above the post — inserted metadata like that should come from you explicitly adding WordPress's own Post Date/Post Author/Post Terms blocks to a post, not from the theme silently rendering it for every post whether you asked for it or not.
